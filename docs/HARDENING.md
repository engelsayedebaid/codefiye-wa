# تقرير الفحص الشامل والتقوية (Full Audit & Hardening)

> **النطاق:** `apps/api`، `apps/worker`، `apps/dashboard`، `packages/*`.
> **المرجع:** طلب «Full Audit & Hardening» بتاريخ 2026-10-03.
> **القاعدة:** لا إعادة كتابة للمشروع. نحدّد السبب الجذري أولًا، ثم نصلحه بأقل تغيير معماري ممكن. كل Migration أو تغيير كاسر مشروح قبل تنفيذه في القسم 3.

---

## 1. ملخص الفحص (Phase 1 — Audit)

حالة البداية: `pnpm typecheck` يمر، و106 اختبارات تمر، والـ dashboard يُبنى. نسخة احتياطية من الكود قبل أي تعديل محفوظة في مجلد العمل المؤقت (`backup-before-hardening.tgz`).

تمت قراءة كل مسارات الـ API والـ worker والـ provider وطبقة الـ DB وكل صفحات الـ dashboard، وقياس زمن كل endpoint على قاعدة Neon الفعلية (us-east-2، حوالي 165ms لكل round trip من مصر):

| Endpoint | الزمن قبل الإصلاح | السبب |
|---|---|---|
| `/health` | ~1ms | بدون DB |
| endpoints بـ SQL مباشر | ~150ms | round trip واحد |
| endpoints بـ drizzle | ~300ms | round tripين لكل query (RC-P1) |
| `/api/me` | ~600ms | 3 queries متتالية عبر drizzle (RC-P2) |
| `/api/messages` | ~750ms | drizzle + جلب عمود `raw` الضخم (RC-P3) |

ما وُجد سليمًا ولا يحتاج تغييرًا:
- **SQL injection:** كل الاستعلامات parameterized (tagged templates أو drizzle). لا يوجد `sql.unsafe` بمدخلات من المستخدم، والبحث في الـ admin يهرّب رموز `LIKE`.
- **IDOR:** كل الموارد (sessions، messages، templates، keys، plan-requests) مفلترة بـ `workspace_id` المأخوذ من الـ token وليس من الـ client. ومفتاح الجلسة `was_` محصور في جلسته فقط.
- **Mass assignment:** كل body يمر عبر Zod `z.object`، الذي يحذف الحقول غير المعرّفة.
- **XSS:** لا يوجد `dangerouslySetInnerHTML` أو `innerHTML`. معاينة القوالب تبني نصًّا عاديًّا.
- **SSRF:** تحميل الوسائط في الـ worker يحجب العناوين الخاصة عند DNS lookup، مع حد 64MB ومهلة 30 ثانية.
- **Secrets:** لا يوجد أي secret في كود الـ frontend أو في الـ build (`dist`).
- صلاحيات الـ admin تُفحص على الـ server (`requireAdmin`)، وليست مجرد إخفاء زر.

## 2. الأسباب الجذرية (Phase 2 — Root Causes)

الخطورة: 🔴 عالية، 🟠 متوسطة، 🟡 منخفضة.

### أ) الأمان

**RC-S1 🔴 — توكن الـ dashboard مخزّن في localStorage**
- **المشكلة:** توكن الدخول (صالح 30 يومًا) محفوظ في `localStorage` ويُرسل في header `Authorization`.
- **السبب:** تصميم مبدئي يعتمد على bearer tokens للـ dashboard أيضًا.
- **الملف:** `apps/dashboard/src/api.ts:3-49`، `App.tsx:64`، `events.ts:14`، `site/Landing.tsx:81`.
- **التأثير:** أي ثغرة XSS، أو أي extension خبيثة، تستطيع سرقة التوكن واستخدامه من أي مكان طوال 30 يومًا.
- **الحل:** session cookie بإعدادات `HttpOnly` و`Secure` و`SameSite=Strict` و`Path=/api`، مع فحص `Sec-Fetch-Site`/`Origin` على كل طلب مُعدِّل (CSRF). الـ bearer tokens تبقى كما هي لعملاء الـ API. والتوكن القديم الموجود في المتصفح يُستبدل تلقائيًّا بـ cookie ثم يُحذف من التخزين.

**RC-S2 🔴 — يمكن تزوير IP العميل وتجاوز كل rate limit مبني على IP**
- **المشكلة:** `trustProxy: true` يجعل Fastify يثق في كل قيم `X-Forwarded-For`، فيصبح `req.ip` هو أول قيمة يرسلها العميل نفسه.
- **الملف:** `apps/api/src/app.ts:38`.
- **التأثير:** المهاجم يغيّر `X-Forwarded-For` مع كل طلب، فيتجاوز حد محاولات الدخول (brute force) وحد التسجيل.
- **الحل:** متغير `TRUST_PROXY` يحدد عدد الـ hops الموثوقة (الافتراضي 1 = بروكسي المنصة فقط)، وبالتالي `req.ip` هو العنوان الذي أضافه البروكسي وليس العميل.

**RC-S3 🔴 — لا حماية فعلية من brute force على تسجيل الدخول**
- **المشكلة:** الحد الوحيد 10 طلبات في الدقيقة لكل IP، في ذاكرة العملية، ولا يوجد حد لكل حساب ولا lockout.
- **الملف:** `apps/api/src/app.ts:86-96`، `routes/account.ts:127-151`.
- **التأثير:** تخمين كلمات المرور من عدة IPs (ومع RC-S2 من IP واحد)، كما أن الحد يُصفَّر عند إعادة تشغيل الـ API.
- **الحل:** جدول `throttles` في Postgres (مشترك بين كل نسخ الـ API ولا يضيع عند إعادة التشغيل). يحسب المحاولات الفاشلة لكل IP ولكل بريد، ويطبّق إيقافًا مؤقتًا يعيد 429 مع `Retry-After`. الرسالة واحدة دائمًا («بيانات الدخول غير صحيحة»)، وscrypt يُحسب حتى لو كان البريد غير موجود حتى لا يختلف زمن الاستجابة.

**RC-S4 🟠 — الطلبات بتوكن خاطئ لا يحدّها أي rate limit**
- **السبب:** الـ rate limiter يعمل في `preHandler` بعد المصادقة، فالطلب الذي يفشل في المصادقة يُرفض قبل أن يُحسب.
- **الملف:** `apps/api/src/app.ts:100-110`، `lib/auth.ts:88-96`.
- **التأثير:** إغراق قاعدة البيانات بعمليات lookup لتوكنات عشوائية (DoS)، لأن cache الأخطاء لا ينفع مع توكن مختلف كل مرة.
- **الحل:** عدّاد في الذاكرة للطلبات الفاشلة لكل IP، يُفحص قبل أي lookup في الـ DB. بعد عدد معيّن من الفشل يعيد 429.

**RC-S5 🟠 — تجاوز حد الخطة بإنشاء توكنات متعددة**
- **السبب:** مفتاح الـ rate limit هو `keyId`، وكل توكن `wap_` جديد يأخذ حصة كاملة.
- **الملف:** `apps/api/src/app.ts:104`.
- **الحل:** الحصة تُحسب لكل workspace مع توكنات `wap_`، ولكل جلسة مع مفاتيح `was_`. لوحة التحكم لها حصة منفصلة كما هو الآن.

**RC-S6 🟠 — scrypt بمعاملات أضعف من توصية OWASP**
- **الملف:** `apps/api/src/lib/passwords.ts:3`، حيث `N=2^14, r=8, p=1`.
- **الحل:** `p=5`، وهو المكافئ الذي توصي به OWASP. الـ hashes القديمة تبقى صالحة وتُعاد كتابتها تلقائيًّا بالمعاملات الجديدة عند أول دخول ناجح.

**RC-S7 🟠 — تغيير كلمة المرور لا ينهي الجلسات الأخرى**
- **الملف:** `routes/account.ts:265-286`.
- **التأثير:** من سرق جلسة يبقى داخل الحساب حتى بعد تغيير كلمة المرور.
- **الحل:** عند تغيير كلمة المرور تُلغى كل جلسات لوحة التحكم ما عدا الجلسة الحالية.

**RC-S8 🟠 — لا توجد security headers**
- **الملف:** `apps/api/src/app.ts`، حيث لا توجد أي headers أمنية.
- **الحل:** `Content-Security-Policy` لصفحة الـ dashboard (مع hash للـ inline script الوحيد)، و`X-Content-Type-Options` و`X-Frame-Options`/`frame-ancestors` و`Referrer-Policy` و`Permissions-Policy` و`Cross-Origin-Opener-Policy`، و`HSTS` عند HTTPS.

**RC-S9 🔴 — إنشاء حسابات بلا تحقق، وبالتالي إنشاء حسابات بالجملة**
- **الملف:** `routes/account.ts:83-125`.
- **التأثير:** كل حساب جديد يحصل على trial مجاني، فيمكن إنشاء عدد غير محدود من الحسابات (spam واستهلاك موارد).
- **الحل:** التسجيل ببريد ورقم هاتف وكلمة مرور، ثم OTP على الهاتف يُتحقق منه على الـ server (التفاصيل في القسم 3). الحساب والـ workspace والـ trial لا تُنشأ إلا بعد التحقق، مع حدود لكل IP ولكل رقم.

**RC-S10 🔴 — لا يمكن إيقاف حساب، وحذف مستخدم يترك بياناته تعمل**
- **المشكلة:** لا يوجد حقل حالة للمستخدم. والعلاقة `workspaces.owner_id` معرّفة بـ `on delete set null`.
- **الملف:** `packages/db/src/schema.ts:23-44`، `lib/auth.ts:55-59`.
- **التأثير:** الـ admin لا يستطيع إيقاف مستخدم مسيء. وحذف صف المستخدم يدويًّا يترك الـ workspace بجلساته ومفاتيحه تعمل بلا مالك.
- **الحل:** `users.status` (`active`/`suspended`) يُفحص في كل مصادقة. الحذف يتم من الـ admin داخل transaction يحذف الـ workspaces بكل ما فيها، ويُسجَّل في `audit_logs`.

**RC-S11 🟡 — logs بلا request id، وإخفاء بيانات ناقص**
- **الملف:** `apps/api/src/index.ts:10-15`، `app.ts:65-81`.
- **الحل:** header `x-request-id` في كل استجابة وفي كل سطر log، ويظهر أيضًا في body أخطاء 500 حتى يذكره المستخدم عند الإبلاغ. يُخفى من الـ logs: `authorization` و`cookie` و`set-cookie` و`x-worker-secret` وحقول `password` و`code`.

**RC-S12 🟡 — الأخطاء بلا `code` ثابت، وأخطاء الـ DB المتوقعة تظهر كـ 500**
- **الملف:** `apps/api/src/app.ts:65-81`.
- **التأثير:** الـ frontend لا يستطيع التفرقة بين أنواع الأخطاء بشكل موثوق. وتعارض unique أو انتهاء مهلة query يظهر كـ «Internal server error».
- **الحل:** حقل `code` يُضاف للاستجابة (إضافة فقط، لا يكسر العقد الحالي). وتحويل أخطاء Postgres: `23505` يصبح 409، و`57014` (انتهاء المهلة) وانقطاع الاتصال يصبحان 503.

### ب) الاستقرار (Backend)

**RC-ST1 🔴 — لا معالجة لأخطاء مستوى العملية**
- **الملف:** `apps/api/src/index.ts`، `apps/worker/src/index.ts`.
- **التأثير:** `unhandledRejection` واحد (يحدث أحيانًا داخل Baileys) يُسقط العملية بلا log مفيد. ولو سقط الـ worker سقطت معه كل جلسات واتساب.
- **الحل:** `unhandledRejection` يُسجَّل في الـ log وتستمر العملية. `uncaughtException` يُسجَّل ثم يُغلق النظام بشكل منظم، والمنصة تعيد التشغيل.

**RC-ST2 🔴 — لا مهلة لأي query ولا للاتصال بقاعدة البيانات**
- **الملف:** `packages/db/src/client.ts:15-19`.
- **التأثير:** query عالقة، أو transaction متروكة مفتوحة، تجعل الطلب ينتظر بلا نهاية (loading لا ينتهي) وتحجز اتصالًا من الـ pool.
- **الحل:** `statement_timeout = 30s` و`idle_in_transaction_session_timeout = 60s` على مستوى الـ role داخل قاعدة التطبيق فقط. وفي الـ client: `connect_timeout` و`idle_timeout` و`max_lifetime`.

**RC-ST3 🔴 — أحداث الـ LISTEN تضيع عند انقطاع الاتصال**
- **المشكلة:** postgres.js يعيد الاشتراك تلقائيًّا بعد الانقطاع، لكن الأحداث التي وصلت أثناء الانقطاع تضيع، ولا يُبلَّغ أحد بأن شيئًا ضاع.
- **الملف:** `apps/api/src/lib/events.ts:9-18`، و`apps/dashboard/src/events.ts`.
- **التأثير:** الـ dashboard يعرض حالة قديمة (جلسة متصلة تظهر غير متصلة، رسالة مُرسلة تظهر في الانتظار)، ولا يتصحح ذلك إلا بعمل refresh.
- **الحل:** عند كل إعادة اتصال يرسل الـ API حدث `resync` لكل متصفح متصل، فيعيد الـ dashboard جلب البيانات. وعند إعادة اتصال الـ SSE نفسه يُعاد الجلب أيضًا.

**RC-ST4 🔴 — الإرسال في الـ worker بلا مهلة**
- **الملف:** `apps/worker/src/runner.ts:224-273`، `packages/provider/src/baileys.ts:388-413`.
- **التأثير:** socket نصف مفتوح يجعل `sendMessage` تنتظر بلا نهاية، فتتوقف كل الرسائل التالية للجلسة نفسها. وفحص «هل الرقم على واتساب» ينتظر حتى 60 ثانية قبل كل رسالة لرقم جديد.
- **الحل:** مهلة 45 ثانية للإرسال. إذا انتهت تُعلَّم الرسالة `failed` ولا تُعاد تلقائيًّا، حتى لا تتكرر (الرسالة توضح أنها ربما وصلت). ومهلة 10 ثوانٍ لفحص الرقم.

**RC-ST5 🟠 — Race condition في حد عدد الجلسات**
- **الملف:** `lib/limits.ts:16-22`، `routes/sessions.ts:57-73`.
- **التأثير:** طلبان متزامنان يتجاوزان حد الخطة، لأن العدّ يحدث خارج الـ transaction.
- **الحل:** قفل صف الـ workspace (`FOR UPDATE`) داخل transaction الإنشاء، ثم العدّ.

**RC-ST6 🟠 — طلبات الخطة المكررة**
- **الملف:** `routes/account.ts:215-228`، ولا يوجد constraint في الـ DB.
- **التأثير:** طلبان متزامنان ينتجان طلبين معلّقين لنفس الـ workspace.
- **الحل:** قفل صف الـ workspace، وunique index جزئي يسمح بطلب `pending` واحد فقط، ورفض تكرار نفس الخطة المعلّقة بـ 409.

**RC-ST7 🟡 — اتصالات SSE**
- **المشكلة:** لا حد لعدد الاتصالات، والاتصال المفتوح لتوكن أُلغي أو لحساب أُوقف يبقى يستقبل الأحداث.
- **الملف:** `routes/events.ts`.
- **الحل:** حد لعدد الاتصالات المتزامنة لكل workspace، وإغلاق فوري لاتصالات الحساب الذي أُوقف.

### ج) التعليق وحاجة الـ Refresh (Frontend)

**RC-F1 🔴 — لا مهلة ولا إلغاء للطلبات**
- **الملف:** `apps/dashboard/src/api.ts:69-94`.
- **التأثير:** إذا تعطّل الاتصال أو علِق الـ server يبقى الـ spinner إلى الأبد، وهذا هو السبب المباشر لـ «loading لا ينتهي».
- **الحل:** مهلة 20 ثانية لكل طلب مع `AbortSignal`. الطلب يُلغى عند مغادرة الصفحة أو تغيير المدخلات.

**RC-F2 🔴 — الخطأ يترك الصفحة في «جاري التحميل» للأبد، بلا زر إعادة**
- **السبب:** الصفحات تعتبر `data === null` معناها أن البيانات تُحمَّل، حتى بعد فشل الطلب.
- **الملف:** `pages/Templates.tsx:517-567`، `pages/Keys.tsx:11-61`، `pages/Admin.tsx:79-118, 225-266`، `pages/SessionDetail.tsx:438-462`.
- **الحل:** الفصل بين حالات loading وerror وempty وsuccess، مع زر «إعادة المحاولة» في كل حالة خطأ.

**RC-F3 🟠 — الردود تصل بترتيب خاطئ (race)**
- **الملف:** `pages/Admin.tsx:229-239` (البحث)، `pages/Dashboard.tsx:236-246` (تغيير المدة).
- **التأثير:** نتيجة بحث قديمة تصل بعد الأحدث فتحل محلها.
- **الحل:** cache مستقل لكل مجموعة مدخلات (query key)، وإلغاء الطلب القديم.

**RC-F4 🔴 — البيانات لا تتجدد إلا بعمل Refresh**
- **السبب:** كل صفحة تجلب بياناتها مرة واحدة عند فتحها، ولا تعيد الجلب عند الرجوع للتبويب أو عودة الإنترنت. وبيانات الحساب تُحمَّل مرة واحدة فقط.
- **الملف:** `app/AppShell.tsx:402-420` وكل الصفحات.
- **الحل:** `@tanstack/react-query`: cache مشترك، وإعادة جلب عند focus أو reconnect، وinvalidation بعد كل تعديل وعند وصول أحداث SSE، وoptimistic updates للحذف، وretry مع backoff للأخطاء المؤقتة فقط (عمليات القراءة فقط، والتعديلات لا تُعاد تلقائيًّا أبدًا).

**RC-F5 🔴 — اتصال SSE لكل صفحة ولكل تبويب، يبقى مفتوحًا حتى في التبويبات المخفية**
- **الملف:** `apps/dashboard/src/events.ts:9-58`.
- **التأثير:** في HTTP/1.1 يسمح المتصفح بـ 6 اتصالات فقط لكل host. مع عدة تبويبات مفتوحة تُستهلك الاتصالات الستة، فتنتظر باقي الطلبات بلا نهاية. هذا سبب «تهنيج» حقيقي يظهر عند فتح أكثر من تبويب.
- **الحل:** اتصال واحد مشترك لكل تبويب، يُغلق عندما يكون التبويب مخفيًّا ويعود عند ظهوره (مع إعادة جلب البيانات).

**RC-F6 🟡 — bundle واحد حجمه 402KB**
- **الملف:** `App.tsx`، حيث تُستورد كل الصفحات مباشرة.
- **الحل:** lazy loading للصفحات. الصفحة الرئيسية لا تحمّل كود لوحة التحكم، والعكس.

### د) الأداء (Database / API)

**RC-P1 🔴 — كل query عبر drizzle تكلّف round tripين**
- **السبب:** drizzle ينفّذ الاستعلامات عبر `client.unsafe(query, params)`، وpostgres.js يجعل `unsafe` تعمل بـ `prepare: false`. ومع وجود parameters يرسل `Describe` أولًا وينتظر الرد قبل التنفيذ.
- **الملف:** `packages/db/src/client.ts:18` (السلوك موجود في `postgres/src/connection.js:238`).
- **التأثير:** كل endpoint يستخدم drizzle أبطأ بالضعف (حوالي 300ms بدل 150ms من مصر).
- **الحل:** تفعيل الـ named prepared statements لاستعلامات drizzle، داخل الـ transactions أيضًا، فتأخذ round trip واحدًا بعد أول تنفيذ على كل اتصال.

**RC-P2 🟠 — `/api/me` ينفّذ 3 queries متتالية**
- **الملف:** `routes/account.ts:183-201`.
- **الحل:** query واحدة بـ joins، فينزل الزمن من حوالي 600ms إلى حوالي 150ms.

**RC-P3 🟠 — قائمة الرسائل تجلب عمود `raw`**
- **المشكلة:** `raw` هو الرسالة الأصلية من واتساب بصيغة JSON، وقد يكون كبيرًا، ولا يُعرض للمستخدم أصلًا.
- **الملف:** `routes/messages.ts:229-253`.
- **الحل:** تحديد الأعمدة المطلوبة فقط.

**RC-P4 🟠 — لا يوجد index على `workspaces(owner_id)`**
- **الملف:** `packages/db/src/schema.ts:35-44`.
- **التأثير:** كل عملية دخول وكل `/me` تمسح جدول الـ workspaces كاملًا (full scan).
- **الحل:** إضافة index.

**RC-P5 🟡 — قائمة الـ admin بلا pagination**
- **المشكلة:** 3 subqueries لكل صف، بحد أقصى ثابت 200 صف.
- **الملف:** `routes/admin.ts:126-152`.
- **الحل:** pagination (`page`/`pageSize` مع `total`)، وفلترة بالحالة.

## 3. خطة التنفيذ والـ Migrations والتغييرات الكاسرة (تُشرح قبل التنفيذ)

### 3.1 Migration `0005_hardening`: إضافية بالكامل، وتحافظ على كل البيانات الحالية

| التغيير | السبب | الأمان أثناء الـ deploy |
|---|---|---|
| `users.role` (`user`/`admin`) مع check constraint، وملؤه من `is_admin` | Roles واضحة | `is_admin` يُستبدل بعمود generated `(role = 'admin')` داخل نفس الـ transaction. الكود القديم الذي يقرأ `is_admin` أثناء الـ deploy يستمر بالعمل |
| `users.status` (`active`/`suspended`) و`suspended_at` و`suspended_reason` | الإيقاف والتفعيل | الافتراضي `active`، فكل المستخدمين الحاليين يبقون كما هم |
| `users.phone` و`users.phone_verified_at`، مع unique جزئي على الأرقام الموثّقة فقط | التحقق من الهاتف | nullable. المستخدمون الحاليون بلا رقم ويُطلب منهم توثيقه لاحقًا |
| جدول `phone_verifications` | OTP: hash فقط بلا plaintext، وصلاحية ومحاولات وcooldown | جدول جديد |
| جدول `throttles` | brute force وحدود الإرسال، مشتركة بين النسخ | جدول جديد |
| جدول `audit_logs` | تسجيل أفعال الـ admin | جدول جديد، بلا FK حتى يبقى السجل بعد حذف المستخدم |
| index على `workspaces(owner_id)` | RC-P4 | إضافة |
| unique جزئي `plan_requests(workspace_id) WHERE status = 'pending'` | RC-ST6 | قبل إنشائه تُلغى الطلبات المعلّقة المكررة القديمة إن وُجدت (يبقى الأحدث) |
| `statement_timeout` و`idle_in_transaction_session_timeout` على مستوى الـ role داخل قاعدة التطبيق فقط | RC-ST2 | best-effort: إذا لم تكن الصلاحية متاحة يُسجَّل NOTICE ولا تفشل الـ migration. لا يمس قاعدة `neondb` القديمة. اتصال الـ migrations يلغي المهلة لنفسه |

### 3.2 تغييرات سلوكية أو كاسرة، ولماذا هي ضرورية

1. **التسجيل يصبح على خطوتين** (مطلوب في التكليف):
   - `POST /api/auth/register` يستقبل `{name, email, phone, password}` ويرد بـ **202** و`{verificationId, phone (مخفي جزئيًّا), expiresAt, resendAfter}`. الرد السابق كان 201 مع token.
   - `POST /api/auth/register/verify` يستقبل `{verificationId, code}` وينشئ المستخدم والـ workspace والـ trial ويضبط الـ cookie.
   - `POST /api/auth/register/resend` يعيد إرسال الكود مع cooldown.
   - المستهلك الوحيد لهذا الـ endpoint هو الـ dashboard، وقد تم تحديثه.
2. **جلسة الـ dashboard تصبح HttpOnly cookie** (RC-S1). ردّا `login` و`register/verify` لا يحتويان `token` بعد الآن.
   - للوصول البرمجي يُستخدم توكن `wap_` من صفحة «المفاتيح»، وهو المسار الموثّق أصلًا. كل bearer tokens (`wap_` و`was_`) تعمل كما هي.
   - `POST /api/auth/session`: الدخول بتوكن `wap_` من صفحة الدخول يتحول إلى cookie. والتوكن القديم المخزّن في المتصفح يُنقل تلقائيًّا ثم يُحذف من `localStorage`، فلا يُطلب من أحد تسجيل الدخول من جديد.
3. **طلب الخطة (طلب الخدمة)** يتطلب حسابًا `active` ورقم هاتف موثّقًا (الـ admins مستثنون). المستخدمون القدامى بلا رقم يظهر لهم تنبيه «وثّق رقم هاتفك» مع نافذة التوثيق نفسها. الدخول والـ API لا يتأثران.
4. **حساب موقوف:** كل طلباته تُرفض بـ 403 و`code: "account_suspended"` مع رسالة واضحة. جلسات الدخول تُلغى، وجلسات واتساب توقف (الأجهزة تبقى مربوطة)، والرسائل التي في الانتظار تُعلَّم `failed`. وعند إعادة التفعيل يدخل المستخدم من جديد ويعيد تشغيل جلساته بضغطة، بلا حاجة لمسح QR.
5. **حقل `code` في أخطاء الـ API:** إضافة فقط. `success` و`message` و`errors` كما هي.

### 3.3 قناة إرسال الـ OTP (credentials في Environment Variables فقط، ولا شيء منها في الـ Frontend)

- `OTP_CHANNEL=sms`: عبر **Twilio Programmable Messaging** باستخدام `TWILIO_ACCOUNT_SID` و`TWILIO_AUTH_TOKEN` و`TWILIO_FROM`. الاتصال بـ REST API مباشرة عبر `fetch` مع timeout، بلا SDK.
- `OTP_CHANNEL=whatsapp`: عبر جلسة واتساب مخصصة للنظام (`OTP_WHATSAPP_SESSION_ID`). الكود يُرسل مباشرة من الـ worker عبر RPC ولا يُكتب في جدول الرسائل.
- إذا لم تُضبط أي قناة يرد التسجيل بـ 503 ورسالة واضحة، مع تحذير في logs الإقلاع.
- الكود: 6 أرقام من `crypto.randomInt`، يُخزَّن كـ `HMAC-SHA256(OTP_SECRET, verificationId:code)`، والمقارنة `timingSafeEqual`. صلاحيته 10 دقائق، و5 محاولات، و60 ثانية cooldown بين الإرسالات، وحدود للإرسال لكل رقم ولكل IP، وحد يومي عام.
