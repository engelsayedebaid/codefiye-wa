# wa-platform — منصّة WhatsApp API

خدمة SaaS تحوّل رقم واتساب عادي إلى REST API (على غرار WasenderAPI): العميل يربط رقمه بمسح QR، يأخذ مفتاح API، يرسل/يستقبل الرسائل والوسائط، ويستقبل Webhooks.

- **المدى:** 12 أسبوعاً حتى الإطلاق
- **الفريق الأدنى:** مطوّر Backend أول + مطوّر واجهات
- **تكلفة البنية عند البداية:** ≈ 60–120 دولار/شهر
- **تاريخ إعداد الخطة:** 16 سبتمبر 2026

## 1. القرار الأساسي: غير رسمي أم رسمي؟

WasenderAPI (وكل منافسيها: Evolution API, WAHA, UltraMsg) تعمل ببروتوكول **WhatsApp Web Multi-Device** عبر مكتبة مفتوحة المصدر — وليس عبر Meta. هذا هو سبب "رسائل غير محدودة بـ 6 دولار": لا تكلفة لكل رسالة، لكن الرقم قابل للحظر والخدمة تعتمد على هندسة عكسية.

### مسار Baileys (غير رسمي) — **الخطة تعتمده**

- مكتبة `@whiskeysockets/baileys` — WebSocket مباشر بلا متصفح، ≈ 30–60 MB لكل جلسة.
- ربط بـ QR أو Pairing Code، إرسال كل أنواع الرسائل، مجموعات، قنوات، حالات.
- لا موافقة من Meta، لا قوالب، لا تكلفة للرسالة.
- الثمن: مخالفة شروط واتساب، احتمال حظر الأرقام، كسر البروتوكول مع كل تحديث.

### مسار Cloud API (رسمي من Meta) — بديل لاحق

- مستقر وقانوني، بلا حظر، ويدعم الأزرار والقوائم الرسمية.
- يتطلب Business Verification، وقوالب معتمدة للرسائل المبادرة.
- تكلفة لكل محادثة (≈ 0.02–0.08 دولار) تُمرَّر للعميل.
- مناسب كـ "Tier رسمي" داخل نفس المنصة في مرحلة لاحقة.

> **قرار يجب توثيقه قبل كتابة سطر واحد:** ابنِ الطبقة الوسطى (API + Webhooks + لوحة + فوترة) بحيث تكون **مستقلة عن المزوّد**: واجهة `Provider` واحدة لها تنفيذان — Baileys الآن، وMeta Cloud API لاحقاً. هذا يحمي المشروع لو تشدّد واتساب في الحظر.

## 2. نطاق المنتج

### MVP (ما يُطلق فعلاً)

- **الجلسات:** إنشاء جلسة، عرض QR حيّ، Pairing Code، حالة الاتصال، فصل/حذف، إعادة اتصال تلقائية.
- **الإرسال:** نص، صورة، فيديو، صوت، مستند، موقع، جهة اتصال — كل ذلك من endpoint واحد `POST /api/send-message` يقبل `to` بصيغة E.164 أو JID.
- **التحقق:** `GET /api/on-whatsapp/:number` هل الرقم على واتساب؟
- **الاستقبال:** Webhooks للرسائل الواردة وحالات التسليم وحالة الجلسة، مع توقيع HMAC وإعادة محاولة.
- **الوسائط الواردة:** رابط تحميل مؤقت + endpoint لفك التشفير.
- **لوحة التحكم:** تسجيل، جلسات، مفاتيح API، سجل الرسائل، إعداد Webhooks، الاشتراك.
- **الفوترة:** 4 خطط بعدد جلسات، تجربة مجانية محدودة، Stripe (+ Paymob للسوق المصري).
- **التوثيق:** صفحة API Docs مولّدة من OpenAPI + مجموعة Postman.

### الإصدار 1.1 (الشهر الرابع)

- المجموعات: إنشاء، إضافة/إزالة أعضاء، رابط دعوة، إعدادات، رسالة بمنشن.
- جهات الاتصال: قائمة، حظر/رفع حظر، صورة الملف، تحويل LID ↔ رقم.
- رسائل متقدمة: رد مقتبس، تعديل، حذف، استطلاع، ملصق، عرض لمرة واحدة، تعليم كمقروء.
- SDK رسمي: Node.js وPython (مولّدان من OpenAPI)، ثم Laravel.

### الإصدار 2 (بعد الإطلاق بـ 6 أشهر)

- القنوات (Newsletters)، عقدة n8n، خادم MCP، صندوق وارد بسيط للردود، وTier رسمي عبر Meta.

## 4. محرّك الجلسات (قلب المنتج)

هنا 60% من صعوبة المشروع. كل جلسة = socket من Baileys + ملفات مفاتيح (Signal keys) يجب حفظها بعد كل رسالة تقريباً.

1. **مخزن حالة مخصص:** لا تستخدم `useMultiFileAuthState` (ملفات) — اكتب `usePostgresAuthState(sessionId)` يحفظ `creds` و`keys` في جدول `session_auth` مشفّراً بـ AES-256-GCM بمفتاح لكل بيئة.
2. **دورة حياة الجلسة:** `created → qr → pairing → connected → disconnected → logged_out`. كل انتقال يُكتب في DB ويُبثّ كـ Webhook `session.status` وكحدث SSE للوحة.
3. **إعادة الاتصال:** عند `connection.close` افحص `statusCode`: `loggedOut` → أوقف نهائياً واطلب QR جديداً؛ غير ذلك → أعد الاتصال بتراجع أسّي (1s, 2s, 4s… حتى 60s) وحد أقصى 20 محاولة ثم علّمها `needs_attention`.
4. **طابور إرسال لكل جلسة:** رسالة واحدة في كل مرة، تأخير عشوائي 1–3 ثوانٍ بين الرسائل، وإظهار "يكتب…" قبل النص — يقلّل الحظر بوضوح.
5. **حالة الرسالة:** استمع لـ `messages.update` لتحويل `pending → sent → delivered → read` وبثّها كـ Webhook `message.status`.
6. **الوسائط الواردة:** لا تُنزّل تلقائياً كل شيء؛ خزّن `url + mediaKey` وانزّل عند الطلب عبر `POST /api/decrypt-media` أو عند تفعيل خيار "تنزيل تلقائي" للعميل.
7. **المشرف (Supervisor):** عملية صغيرة تعرف أي عامل يحمل أي جلسة (خريطة في Redis). عند سقوط عامل، يعيد توزيع جلساته على عمّال أحياء خلال 30 ثانية.
8. **عزل الأعطال:** كل عامل في حاوية بحدود ذاكرة؛ جلسة تسرّب الذاكرة لا تُسقط 99 جلسة معها.

### نموذج أولي في 40 سطراً — نفّذه في اليوم الأول

```ts
// poc.ts — يربط رقماً بـ QR ويوفّر POST /send
import makeWASocket, { useMultiFileAuthState, DisconnectReason } from '@whiskeysockets/baileys';
import Fastify from 'fastify';
import qrcode from 'qrcode-terminal';

async function start() {
  const { state, saveCreds } = await useMultiFileAuthState('./auth');
  const sock = makeWASocket({ auth: state, printQRInTerminal: false });
  sock.ev.on('creds.update', saveCreds);
  sock.ev.on('connection.update', ({ connection, qr, lastDisconnect }) => {
    if (qr) qrcode.generate(qr, { small: true });
    if (connection === 'close' && lastDisconnect?.error?.output?.statusCode !== DisconnectReason.loggedOut) start();
  });
  sock.ev.on('messages.upsert', ({ messages }) =>
    console.log('IN', messages[0]?.key.remoteJid, messages[0]?.message?.conversation));

  const app = Fastify();
  app.post('/send', async (req) => {
    const { to, text } = req.body as { to: string; text: string };
    const jid = to.replace(/\D/g, '') + '@s.whatsapp.net';
    return sock.sendMessage(jid, { text });
  });
  await app.listen({ port: 3000 });
}
start();
```

```bash
npm i @whiskeysockets/baileys fastify qrcode-terminal
npx tsx poc.ts
curl -X POST localhost:3000/send -H 'Content-Type: application/json' -d '{"to":"+2010XXXXXXXX","text":"hello"}'
```

## 6. تصميم الـ API

حافظ على توافق شبه كامل مع شكل WasenderAPI (نفس المسارات والحقول) — يسهّل على عملائهم الانتقال إليك ويجعل الأمثلة والـ SDKs مألوفة. المصادقة: `Authorization: Bearer <key>`؛ مفتاح الجلسة يحدد الجلسة ضمنياً، وPAT يتطلب `X-Session-Id`.

| المسار | الوظيفة | الأولوية |
|---|---|---|
| `POST /api/send-message` | نص/صورة/فيديو/صوت/مستند/موقع/جهة اتصال حسب الحقول الموجودة (`text`, `imageUrl`, …) | MVP |
| `GET /api/on-whatsapp/:id` | هل الرقم/الـ JID على واتساب | MVP |
| `GET /api/messages/:id` · `POST /api/messages/:id/resend` | حالة رسالة · إعادة إرسال الفاشلة | MVP |
| `POST /api/upload` · `POST /api/decrypt-media` | رفع وسائط للإرسال · فك تشفير وسائط واردة | MVP |
| `GET/POST /api/whatsapp-sessions` · `/:id/connect` · `/:id/qrcode` · `/:id/pairing-code` · `/:id/disconnect` · `DELETE` | إدارة الجلسات برمجياً (بـ PAT) | MVP |
| `GET /api/status` | حالة الجلسة الحالية + الرقم المربوط | MVP |
| `/api/webhooks` CRUD · `/api/webhooks/:id/test` | إدارة الـ Webhooks واختبارها | MVP |
| `/api/groups/*` (14 مساراً) | إنشاء، أعضاء، دعوة، إعدادات، صورة، مغادرة | 1.1 |
| `/api/contacts/*` · `/api/lid/*` | جهات الاتصال، الحظر، LID ↔ رقم | 1.1 |
| `PUT/DELETE /api/messages/:id` · `/api/messages/:id/read` · `/api/send-poll` | تعديل، حذف، قراءة، استطلاع | 1.1 |
| `/api/channels/*` | القنوات | 2.0 |

### عقود ثابتة من اليوم الأول

- **شكل النجاح:** `{ "success": true, "data": { … } }` — **شكل الخطأ:** `{ "success": false, "message": "…", "errors": { "field": ["…"] } }` مع رموز HTTP: 400 / 401 / 402 (لا اشتراك) / 404 / 409 (الجلسة غير متصلة) / 422 / 429.
- **ترويسات Rate limit:** `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After`. الحد لكل خطة (مثلاً Basic: 60 طلباً/دقيقة/جلسة، Trial: 10 رسائل/ساعة).
- **Idempotency-Key** اختياري على الإرسال لمنع التكرار عند إعادة المحاولة من العميل.
- **إصدار API:** عبر ترويسة `X-API-Version: 2026-09-01` لا عبر المسار، لتبقى المسارات متوافقة.

## 7. الـ Webhooks

الأحداث المطلوبة للتكافؤ مع WasenderAPI (سمّها بنقطة لا بمسافة):

- **الرسائل:** `messages.received`, `messages.sent`, `messages.update` (الحالة), `messages.delete`, `messages.reaction`, `poll.results`, `call.received`.
- **الجلسة:** `session.status`, `qrcode.updated`, `pairing.updated`.
- **الدفاتر:** `chats.upsert/update/delete`, `contacts.upsert/update`, `groups.upsert/update`, `group-participants.update`.

التنفيذ:

- **الحمولة:** `{ event, timestamp, sessionId, data }` — أرسل `data` بشكل Baileys الخام مضافاً إليه حقول مبسّطة (`from`, `text`, `mediaUrl`) حتى لا يحتاج العميل لفهم بنية Signal.
- **التوقيع:** ترويسة `X-Webhook-Signature: sha256=HMAC(secret, timestamp + "." + body)` + `X-Webhook-Timestamp` لمنع إعادة التشغيل (Replay).
- **التسليم:** مهلة 10 ثوانٍ، إعادة محاولة أسّية 6 مرات (1د، 5د، 30د، 2س، 6س، 24س)، ثم تعطيل الرابط تلقائياً بعد 50 فشلاً متتالياً مع إيميل تنبيه.
- **الشفافية:** صفحة "سجل التسليم" في اللوحة تعرض كل محاولة والرد، مع زر إعادة إرسال يدوي.

## 8. لوحة التحكم

- **الجلسات:** بطاقة لكل جلسة (الاسم، الرقم، الحالة بلون، آخر نشاط). زر "ربط" يفتح QR يتحدث حياً عبر SSE كل 20 ثانية مع خيار Pairing Code.
- **مفاتيح API:** إنشاء، تسمية، نطاقات، عرض المفتاح مرة واحدة فقط، إلغاء.
- **الرسائل:** جدول قابل للبحث بالرقم/التاريخ/الحالة، مع تفاصيل الخطأ للفاشلة و"إرسال تجريبي" من اللوحة.
- **Webhooks:** الروابط، الأحداث المشتركة، السر، سجل التسليم، زر اختبار.
- **الاستخدام والفوترة:** رسم بياني للرسائل يومياً، الخطة الحالية، الفواتير، الترقية.
- **الفريق:** دعوة أعضاء بأدوار (مالك، مطوّر، مشاهد).
- **التوثيق:** صفحة Docs مولّدة من OpenAPI (Scalar أو Redoc) بأمثلة cURL/Node/Python لكل مسار.

- **المزوّد:** Stripe للعالم (Checkout + Customer Portal + Webhooks `invoice.paid` / `customer.subscription.updated`)، وPaymob أو Fawry للدفع بالجنيه.
- **التطبيق:** Middleware واحد يقرأ الخطة من الكاش ويرفض إنشاء جلسة إضافية أو يرجع 402 عند انتهاء الاشتراك، مع فترة سماح 3 أيام تُبقي الجلسات متصلة لكن توقف الإرسال.
- **مكافحة الاحتيال:** التجربة تتطلب بطاقة أو رقم موثّق بـ OTP (لديك الوحدة جاهزة)، وحد أقصى لجلسات التجربة لكل IP.

## 10. الأمان ومنع الحظر

### الأمان

- مفاتيح API مخزّنة كـ SHA-256؛ حالة الجلسة مشفّرة؛ أسرار الـ Webhook مشفّرة؛ TLS في كل مكان؛ 2FA للوحة.
- عزل كامل بين الـ workspaces على مستوى الاستعلامات (كل استعلام يمرّ بـ `workspace_id`)، واختبار آلي يحاول الوصول العابر.
- روابط الوسائط موقّعة ومؤقتة (15 دقيقة)، وفحص MIME للرفع، وحد حجم 64 MB.
- سجل تدقيق لكل عملية حساسة، وتنبيه عند تسجيل دخول من جهاز جديد.

### منع الحظر (سُمعة الأرقام هي المنتج الحقيقي)

- **تسخين الأرقام:** الجلسات الجديدة محدودة بـ 20 رسالة/ساعة لأول 3 أيام، ثم ترتفع تدريجياً.
- **سلوك بشري:** تأخير عشوائي، "يكتب…" قبل الإرسال، عدم الإرسال لأرقام غير موجودة على واتساب (افحص أولاً)، ونسبة رد واردة/صادرة تُراقَب.
- **قواعد استخدام مقبول:** منع الرسائل الجماعية غير المرغوبة، تعليق تلقائي لجلسة تتجاوز 40% رسائل لأرقام جديدة بلا رد، وإجراء KYC خفيف لخطط Business.
- **عزل الشبكة:** IP مختلف لكل مجموعة جلسات (Proxies سكنية للخطط العليا) حتى لا يتأثر الجميع بحظر جلسة واحدة.

> **الالتزام القانوني:** اكتب شروط خدمة صريحة: الخدمة غير تابعة لـ Meta، المستخدم مسؤول عن الالتزام بشروط واتساب وقوانين مكافحة الرسائل المزعجة، والأرقام قد تُحظر. أضف سياسة خصوصية وDPA لأنك تخزّن محادثات عملاء عملائك.

### حالة التنفيذ (3 أكتوبر 2026)

أُعيد بناء المشروع من هذه الخطة. المنجز: أسبوع العمل الأول + نواة المرحلة 1.

- **محرّك الجلسات:** مشرف موزّع في كل عامل (نبض كل 5 ثوانٍ، استرداد جلسات العامل الساقط خلال 30 ثانية)، إعادة اتصال بتراجع أسّي حتى 20 محاولة ثم `needs_attention`، حالة دخول مشفّرة AES-256-GCM في `session_auth`، طابور إرسال متسلسل لكل جلسة مع تأخير عشوائي و"يكتب…"، فحص الرقم على واتساب قبل الإرسال، وتتبّع `sent → delivered → read`.
- **الـ API:** المسارات المتوافقة مع WasenderAPI للجلسات والإرسال (`/api/send-message` بكل الأنواع، `on-whatsapp`، `status`، `messages/:id`، `resend`)، مفاتيح جلسات `was_` ورموز مساحة عمل `wap_`، Idempotency-Key، حدود الخطة (عدد الجلسات، الطلبات/دقيقة، رسائل التجربة اليومية، انتهاء التجربة → 402)، توثيق OpenAPI على `/docs`، وبثّ SSE على `/api/events`.
- **لوحة التحكم:** دخول برمز مساحة العمل، الجلسات، QR حيّ ورمز ربط، إرسال تجريبي، سجل الرسائل، مفاتيح API.
- **انحراف مقصود عن §3:** لا Redis/BullMQ حالياً — Postgres هو الطابور (`messages` + `SKIP LOCKED`) وقناة الأحداث (`LISTEN/NOTIFY`). يكفي لمرحلة الإطلاق ويقلّل البنية؛ يُعاد تقييمه عند الاقتراب من 1,000 جلسة.
- **التالي (المرحلة 2):** Webhooks بالتوقيع وإعادة المحاولة، فك تشفير الوسائط الواردة ورفع الملفات (R2)، نقل وحدة المصادقة من CodeFiye، Stripe.
