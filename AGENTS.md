# AGENTS.md

WhatsApp REST API platform — the plan is `README.md` (Arabic). pnpm monorepo (pnpm 12, Node 22+, TypeScript 7, ESM).
Internal packages export TS sources directly (`exports: ./src/index.ts`) and run with `tsx` — no build step except the dashboard. Use extensionless relative imports.

## Layout
- `apps/api` — Fastify 5 + Zod (`fastify-type-provider-zod`). OpenAPI + Scalar at `/docs`. Bearer auth on `api_keys` (SHA-256): `was_…` session keys, `wap_…` workspace tokens (+ `X-Session-Id`). Rate limit per plan. SSE at `/api/events`.
- `apps/worker` — owns Baileys sockets. `Supervisor` (one per worker) heartbeats into `workers`, claims sessions with `desired_state = 'running'` via SKIP LOCKED, drops ones it no longer owns. `SessionRunner` = one session: reconnect backoff, serialized send queue with pacing, receipts, inbound. Internal RPC on `WORKER_PORT` (secret-protected) for live-socket calls (pairing code, on-whatsapp, logout).
- `apps/dashboard` — React 19 + Vite 8 + Tailwind 4. Arabic (RTL, default) and English (LTR): all copy lives in `src/i18n/ar.ts` (source of truth, `Dict` type) and `en.ts`; components read it with `useI18n()` — never hardcode UI strings. Use logical utilities (`ms-`, `start-`, `ps-`) and `flip` for directional icons. Landing at `/`, email/password (or `wap_…` token) login, History-API routing (`src/router.tsx`). App pages: `/dashboard`, `/sessions`, `/templates`, `/keys`, `/subscription`, `/admin` (admins only) — never start a page path with `/api` or `/docs` (the Vite proxy and the API's SPA fallback send those to the API). Look follows the WasenderAPI site/dashboard (shadcn neutral tokens in `src/index.css`, inset sidebar shell); the scraped reference folder was removed. Themes: dark (default for new visitors), light (off-white page, white cards, teal `#367a6b` brand), system — `src/theme.tsx` sets `<html data-theme>`, saved as `wa.theme` (pre-paint script in `index.html`). Light values override the same `--color-*` tokens under `:root[data-theme='light']` (including pale palette shades like `red-400`, remapped darker), so use tokens; text on `bg-brand` is `text-on-brand`, gradients `from-grad-from to-grad-to`; for the rest use the `light:`/`dark:` variants. Icons come from `src/icons` (never `lucide-react` directly): Iconly v2 Light (`src/icons/iconly.ts`, converted from react-iconly, MIT) under the names the call sites use where Iconly has the icon, lucide for the rest, all at a 1.5px line (`LucideProvider` in `main.tsx`); every icon is a `LucideIcon`. Use `Select` from `ui.tsx`, never a native `<select>` (its popup ignores the dark theme). Motion: `animate-fade-up` + `delay()`, `<Reveal>` for scroll-in, `.lift` for hover; all honor `prefers-reduced-motion`.
- `packages/provider` — `Provider` interface (README §1), `BaileysProvider`, `useEncryptedAuthState` (AES-256-GCM, AAD = `sessionId:type:id`).
- `packages/db` — Drizzle schema (snake_case casing), migrations in `packages/db/migrations`, queue helpers, `pgAuthStore`.
- `packages/shared` — response contract, Zod `sendMessageBody`, JID utils, statuses, event types, plans.

## Architecture notes
- **No Redis.** Postgres is the queue and the bus: outbound `messages` rows are the per-session send queue (`queued → sending → sent → delivered → read`); `NOTIFY wa_control` (API → workers) and `NOTIFY wa_events` (workers → API → SSE). LISTEN uses `DATABASE_URL_UNPOOLED`.
- Every session write from a worker is fenced on `worker_id = me`; a worker that lost ownership stops instead of clobbering.
- A WhatsApp session must never be open on two workers at once: WhatsApp logs a linked device out (401, `Stream Errored (conflict)`) when it sees it connected twice. So a session is taken over only after its owner's heartbeat is 60 s old, and a worker whose heartbeat hasn't reached the database for 30 s closes its sockets itself (`Supervisor.fenceAll` → `SessionRunner.fence`, socket first). The heartbeat has its own timer, apart from the reconcile pass. `WORKER_CLAIM` (config.ts) decides whether a worker runs sessions at all: on when deployed (`NODE_ENV=production`, Railway), off on a dev machine, whose worker then hands back any session it holds — the dev database is the production one.
- WhatsApp credentials (`session_auth`) are written only through `pgAuthStore(sql, id, { workerId })`, fenced on `sessions.worker_id` with a share lock (a stale worker gets `AuthFenceError`, never retried). Each `keys.set` is one statement (fence CTE + upserts + deletes; values bound as hex): Baileys awaits it on every encrypted send/receive, so keep it to one round trip. Creds saves are serialized/coalesced/retried and flushed on stop. A failed load is retried, never treated as "no session". Credentials are wiped only by an explicit logout/delete, or after WhatsApp answers 401 twice (the first 401 stops the session and keeps them; the next connect re-tries them). Transient failures never stop a session (`needs_attention` = still retrying every 5 min); only 403 stops it. Keep `AUTH_ENCRYPTION_KEY` backed up: without it every stored session is unrecoverable.
- A message stuck in `sending` after a crash is marked `failed` (never auto-resent → no duplicates); clients resend explicitly.
- `createDb()` returns two postgres.js clients on purpose: drizzle rewrites the parsers of the client it wraps (timestamps → strings, `sql.json` stops serializing). Use `sql` for raw queries, `db` for drizzle.
- Outbound media is downloaded by the worker (`apps/worker/src/media.ts`) with SSRF protection (private ranges blocked at DNS-lookup time), 64 MB cap, 30 s timeout.

## Commands
- Install: `pnpm install`
- Typecheck everything: `pnpm typecheck`
- Tests: `pnpm test` (vitest; DB integration suites need `TEST_DATABASE_URL`, otherwise skipped)
- Dev: `pnpm dev` (api :4000, worker RPC :4100, dashboard :5173 proxying `/api` + `/docs`) or `pnpm dev:api|dev:worker|dev:dashboard`
- Create workspace + token: `pnpm bootstrap <email> "<workspace>" [plan]`
- Create/promote an admin (internal `unlimited` plan, no expiry; prints a generated password): `pnpm admin:create <email> ["Name"] [--reset-password] [--reset-2fa]`
- Schema change: edit `packages/db/src/schema.ts` → `pnpm db:generate` → `pnpm db:migrate` (API and worker also migrate on boot, under an advisory lock)
- Baileys POC (file auth in `./auth`, port 3001): `pnpm poc`

On Railway the worker binds `::` and registers `http://<RAILWAY_PRIVATE_DOMAIN>:4100`, so the API reaches it over the private network. When the API can't connect to the owning worker's URL at all (dev API ↔ Railway worker, or a loopback dev worker ↔ the deployed API), `WorkerClient` relays the call through Postgres instead (`NOTIFY wa_control` type `rpc` → the owner answers on `wa_rpc`; `apps/api/src/lib/workers.ts`, `Supervisor.answerRpc`), so OTP, pairing codes and the other RPCs still work across networks — only answers above the 8 KB NOTIFY cap fail (`too_large`). A worker that was reached but is slow is never retried through the relay (no double sends).

## Conventions
- Pin exact dependency versions; prefer versions published ≥ 7 days ago.
- Build scripts are gated via `allowBuilds` in `pnpm-workspace.yaml`.
- API responses: `{ success: true, data }` / `{ success: false, message, errors? }`. Validation → 422 with `errors: { field: [..] }`.
- Paths and the send-message body/response follow WasenderAPI (`/api/send-message`, `msgId`); other payloads are camelCase.
- Templates: `message_templates` per workspace with `{{var}}` placeholders (logic in `packages/shared/src/template-text.ts`, zod-free so the dashboard can import it). `POST /api/send-message` takes `template` + `variables` instead of `text`; `POST /api/send-otp` generates/sends/returns a code (template `otp` if present, else a built-in text). Templates may add `imageUrl` (sent as one image+caption "card") and `buttons` (2–12; queued as a second message, a WhatsApp poll titled `buttonsTitle`, in the same transaction; response has `pollMsgId`). WhatsApp Web (Baileys) cannot send real buttons/lists — those need the official Cloud API, so polls stand in. Poll votes need the poll's `messageSecret`: `markSent` stores the sent poll in `messages.raw`, the provider's `loadMessage` reads it back, and votes land in `content.votes` (voter → options) with a `poll.vote` event.
- Chats (`/chats`, admins only, the admin's own numbers): `chats` rows (one per session × contact; unread, counters, pin/archive) are maintained by a statement-level trigger on `messages` (migration 0010) — never write them from app code except read/flags/group names (`packages/db/src/chats.ts`). One contact = one chat: `contact_lids` (LID → phone JID, fed by Baileys' `lid-mapping` key writes, a backfill on each runner start, and messages naming both) makes the trigger file LID messages under the phone JID (`alt_jid` = the LID, unique per session); learning a pair merges the LID's chat (migration 0013). Pairs and chat writes take `chat_lock(session)` first. Messages keep their address; read history under both. Names: `chat_display_name()` = address-book name (`contact_names`, from Baileys `contacts.upsert` app-state sync) → verified business name → pushName (`chats.name`); groups keep their subject; masked numbers (`+20∙∙∙16`) are never names. Full sync = `sync_jobs` run by the worker (`apps/worker/src/sync.ts`, `SYNC_CONCURRENCY` slots per worker), resumable, live via `sync.progress`/`sync.log`. Group senders: inbound `content.from` is the member (`participantOf`: in the key on live messages, *beside* it on history-sync ones); a row whose `from` is the group itself lacks its sender — every sync job first re-asks the phone for those pages (`senderlessTarget`, `repairSenders`; the history upsert fills `from` in). The messages route returns `senders` (name: address book → latest pushName; phone via `contact_lids`), and `GET /:id/group-members` lists members live (worker RPC). Messages sent from the phone are stored as outbound rows with `content.sentFrom = 'phone'` (excluded from the daily quota and from opt-out handling). Inbound `content` carries `MessageExtras` (`@wa/shared/chats`: media + base64 preview, location, contacts, quoted, reactTo). Media streams from `/api/chats/media/:id` (decrypted from `raw` in the API, cached with Range support; expired links re-uploaded via worker RPC). Attachments upload to `media_uploads` and are sent as `upload:<id>` URLs the worker reads from the DB. Sending from the page goes through `app/chats/outbox.ts`: an optimistic "queued" bubble at once, requests serialized per number (order kept), each with an `Idempotency-Key` (retries never duplicate; the stand-in drops when the real row lands). Temporary failures (no answer, timeout, 429, 5xx) retry on their own (1.5/4/10/20 s; offline waits for `online`), uploads go by XHR for a progress bar, and unsent text survives a reload (`wa.outbox`, resumed by `restoreOutbox`). A stored failed message can be sent again (`POST /:id/resend`: a copy queued at the end, the failed row removed with `message.changed`; campaign rows excluded; the bubble asks twice when it may have arrived). A number in `connecting` still takes messages (queued until it's back); `LiveBanner` says so when the event stream is down for a few seconds. Those rows carry `content.sentFrom = 'chats'` (+ `reachable: true` when the contact has written in, which skips the worker's "on WhatsApp?" lookup), which skips the worker's artificial "typing…" pause (the inter-message gap stays; API and campaign sends are paced as before). `POST /:id/send` does its lookups in parallel and inserts + both NOTIFYs in one statement. Voice notes are recorded in the composer (`VoiceRecorder.tsx`); Chrome/Edge WebM is remuxed to Ogg/Opus in the browser (`voice.ts`, no re-encode) and sent with `ptt` + `seconds`. Emoji picker data is `emojibase-data`, lazy-loaded. Presence needs the account online: `watch-chat` RPC keeps a 75 s lease, renewed by the open page every minute. Bubbles offer edit (our text messages, 15 min) and delete (`MessageActions.tsx`): for everyone = WhatsApp revoke within 2 days (another member's message only in a group where we are admin — the worker checks, since WhatsApp would silently ignore it), applied with `applyMessageRevoke`; for me = `removeStoredMessage` plus a best-effort `chatModify deleteForMe` to the phone (`synced` in the response). Both go through worker RPC `edit-message`/`delete-message` and publish `message.changed`.
- Login + 2FA (`apps/api/src/routes/account.ts`, `lib/totp.ts`): two-factor (authenticator app, TOTP) is mandatory — a dashboard session of a user without it gets 403 `two_factor_required` on everything but `/api/me`, `/api/account/2fa*` (gate in `app.ts`), and the dashboard shows only the setup screen. Login is steps on a `login_attempts` row (client holds id + secret token): password → code to the verified phone (`phone_verifications.purpose = login`; skipped if the OTP channel is down or the number unreachable) → TOTP. No approval from other devices: an open session elsewhere doesn't change the steps. A recovery code (10, single-use) replaces TOTP and ends all other sessions. The TOTP secret is AES-GCM sealed under a key derived from the OTP HMAC key: changing `OTP_SECRET` (or `WORKER_SECRET` when it is unset) forces everyone to re-enrol. `wap_…` token logins (`/auth/session`) skip these steps.
- Plans: customers request a plan (`POST /api/plan-requests`); an admin approves it in `/admin`, which sets `plan_id` + `plan_expires_at`. An expired trial or paid plan returns 402 on connect/send (`assertActive`). Payment is manual: the admin configures receiving accounts in `/admin` → payment methods (`settings.payment_methods`, `@wa/shared/payments`: Vodafone Cash, InstaPay, bank transfer + USD→EGP rate); when at least one is enabled, a priced plan request must carry `months`, `payment` (per-method sender details) and `proof` (a screenshot, shrunk in the browser to JPEG ≤ 2 MB, stored in `plan_requests.proof`, served to admins at `/api/admin/plan-requests/:id/proof`). Approval defaults to the paid months.
- AI auto-reply agent (`/auto-reply`, admins only; API in `apps/api/src/routes/auto-reply.ts`, engine in `apps/worker/src/autoreply.ts`). Providers are platform-wide (`ai_providers`, one row per provider; its keys in `ai_provider_keys`, several per provider, each sealed with a key derived from `AUTH_ENCRYPTION_KEY` — the API seals and the worker opens, so without that env the panel answers 503; the first key switches the provider on). `AiKeyManager` (worker) rotates keys: a 429 rests only that key (Gemini's `RESOURCE_EXHAUSTED` and OpenAI's "…in organization…" are per-key limits); only an exhausted balance (`insufficient_quota`/billing) rests the whole provider; a 5xx is retried once; timeouts never rest anything. Gemini 2.5+ thinking is paid from `maxOutputTokens` (`geminiGenerationConfig` turns it off on 2.5 Flash, adds headroom elsewhere). `maxReplies` counts the last 10 minutes of a chat (bot-loop guard), not its lifetime. Replies pass `formatForWhatsApp` (`@wa/shared`). One phone linked as two sessions gets every message twice: only `autoReplyOwner` (the oldest connected session of that phone with the agent on) answers. Conversation summaries: a number may set `summary_phone` + `summary_idle_minutes`; every minute the supervisor calls `AutoReplyAgent.summarize` for its connected sessions, which finds chats the agent answered that went quiet (`dueSummaries`), claims each through the unique key of `auto_reply_summaries` (never sent twice; a later message gets a new one), asks the model (`buildSummaryPrompt`), and queues it to that phone from the same session. The contact's name and number in the header come from WhatsApp (`summaryContact`, LIDs through `contact_lids`), never from the model; the agent never answers the summary phone; each number has its own settings (`auto_reply_settings`: on/off, personality or custom prompt, provider + model and a fallback, temperature/max tokens, the pause before replying, business hours in a named time zone, max replies per conversation, ignore list, keyword rules, `{{business_name}}`-style variables); `auto_reply_log` keeps every answer and the interesting skips (activity + statistics). The **worker** runs the agent because it owns the socket: on an inbound direct-chat message it checks the rules, asks the provider over plain `fetch` (Anthropic and Gemini shapes, OpenAI-compatible for OpenAI/Groq/Mistral/custom — `@wa/shared/ai`, no SDKs), and queues the answer as an ordinary outbound row (`content.sentFrom = 'auto'`, `reachable: true`) with `not_before = now() + delay`, so the send queue paces it and a "typing…" shows (the supervisor's 5 s tick picks up delayed rows). The fallback provider answers when the first fails; a keyword rule skips the model; "stop"/"start" stays with the campaign opt-out. Personalities and `buildSystemPrompt` live in `@wa/shared/auto-reply` (Arabic and English versions of each prompt).
- User activity (`/admin` → Overview / User activity / Activity log; `apps/api/src/lib/activity.ts`, `routes/admin-activity.ts`): the dashboard pings `POST /api/activity` on each page and every minute while the tab is visible and in use (`app/activity.ts`, no query strings); pings < 5 min apart extend the user's `user_visits` row (came in = `started_at`, left = `last_seen_at`, `active_seconds` ≤ 60 per ping). `user_events` holds sign-ups, logins (+ failed, with reason; unknown accounts by identifier), logouts, password resets, page views and every dashboard write (`onResponse` hook, `action` with method/route/status; chat traffic and the ping are skipped). Pruned after 180 / 365 days. Admin numbers are counted in the browser's time zone (`tz`).
- Public site (`src/site`: landing, `/guide`, `/privacy`) shares `SiteChrome.tsx` (header/footer/section headings) and the `.site-card`/`.kicker`/`.band` classes in `index.css`. The landing's explainer video and YouTube channel come from `settings.site` (`@wa/shared/site`; public `GET /api/site`, admin `PUT /api/admin/site`, edited in `/admin` → Website). The player is youtube-nocookie, loaded only on play — the dashboard CSP allows just that frame origin.
- Dashboard UI fonts: Instrument Sans (Latin) + IBM Plex Sans Arabic; code: IBM Plex Mono. Wrap phone numbers/keys in `.ltr`.
